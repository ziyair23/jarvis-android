## Problems

### 1. MAJOR: after the first comeback, later held requests can be silently lost
- **Repro:** at 7:10 AM a dead spot holds a request, and signal returns → catch-up spoken, and `signalWatch` runs `Held.onHold = null`. At 7:40, a second short dead spot: cellular still VALIDATED, "Jarvis, what time does Costco open" → two timeouts → held. `onHold` is null, so `netDown` stays false. `reportBad()` makes Android re-check, but the dead spot is short, so the re-check **passes** and VALIDATED never drops. Every later `onCapabilitiesChanged` (validated) returns early on `!netDown`. **Nothing is ever said.** The request expires after 45 min, or gets answered much later on some unrelated network change.
- **Fix (JarvisService.kt):** remove `Held.onHold = null` from `signalWatch.onCapabilitiesChanged`. Clear it only in `onDestroy` (`Held.onHold = null`). Also add a safety net so a hold never depends on a capability change arriving: in `onCreate`, use `Held.onHold = { netDown = true; main.removeCallbacks(signalBack); main.postDelayed(signalBack, 30_000) }` (see problem 2 for the check that makes this safe).

### 2. MAJOR: "Signal's back, sir." can still be said inside the dead spot
- **Repro:** cellular VALIDATED, request held → `onHold` sets `netDown = true` → `reportBad()` starts Android's re-check, which takes up to ~10 s while data is dead. During that window a validated capabilities update (link-bandwidth estimate) arrives → `netDown && count>0` → `signalBack` is posted for 2.5 s later. The re-check then fails and VALIDATED drops, but the unvalidated branch only sets `netDown = true` and **doesn't cancel** the posted `signalBack`. `signalBack` runs, `takeDue` empties the list, the catch-up call fails → `""` → he hears "Signal's back, sir. You'd asked …" with no signal.
- **Fix (JarvisService.kt):**
  1. In `onLost` and in the unvalidated branch, add `main.removeCallbacks(signalBack)`.
  2. Before `Held.takeDue` in `signalBack`'s thread, confirm the network really works:
     ```kotlin
     if (!brain.isValidated() || !brain.reachable()) { netDown = true; if (Held.count() > 0) main.postDelayed(signalBack, 30_000); return@thread }
     ```
     In `Brain.kt`:
     ```kotlin
     fun isValidated() = validated()   // make the existing check public
     fun reachable(): Boolean = try {
         val c = URL("https://api.anthropic.com/").openConnection() as HttpURLConnection
         c.requestMethod = "HEAD"; c.connectTimeout = 3000; c.readTimeout = 3000
         c.responseCode; c.disconnect(); true          // any HTTP answer means the internet works (free, no API call)
     } catch (_: Exception) { false }
     ```
     With the 30 s safety net from problem 1, held items are answered within about 30 s of data really working, and never while it's still dead. Spec AT 6 (Claude unreachable **after** signal returns → reminder) still holds, because the probe only checks the network.

### 3. MEDIUM (Fast): validated-but-dead read timeouts still take ~61 s
- **Repro:** a request on a validated cellular network that connects but gets no bytes back: read timeout 30 s → retry → 30 s → held. That's about 61 s, with "Still on it, sir." at 7 s.
- **Fix (Brain.ask catch branch):** treat a first `SocketTimeoutException` with `!voice.spoke && !didSomething` as dead whatever the validation state: `if (e is java.net.SocketTimeoutException && retried == 0 && !didSomething) { reportBad(); return Held.add(text, now) }` (held == null is already guaranteed there). Optionally lower `readTimeout` in `post()` to 20000. The spec's "instead of failing after a long wait" is the reason this matters.

### 4. COSMETIC: Brain doc comment on the wrong function
`Brain.kt:90`: the "Ask Jarvis something … [held] …" KDoc sits on `private fun validated()`. Move it to just above `fun ask(` and give `validated()` its own: `/** True when Android has checked this network really reaches the internet. */`.

### 5. NOTE: dead check in `signalBack`
`r == Held.HELD_LINE` can't happen any more (held asks skip the offline hold). It's harmless, and can be removed.
