## Problems
1. **High (fails test 3) — edge windows built from one hour win.** Windows start on every hour and only need 4 offers total, so the 6–8 AM window contains only his 7 AM offers. When 7 AM is even slightly better than 8 AM (normal), "6 AM to 8 AM" wins; on a tie it also wins because it comes first. Same for the weakest window ("4 PM to 6 PM" when he starts at 5).
   Repro (`l1_t3_realisticMorningNamesSevenToNine`): 8 offers at 7 AM ($8.40/3 mi), 8 at 8 AM ($7.80/3 mi), 10 at 5–6 PM ($4.80/3 mi) → "Your best stretch is 6 AM to 8 AM, about 2.80 dollars a mile … from 8 offers." Expected 7 AM to 9 AM, 16 offers. `l1_t3_weakestMustBeHoursHeWorked` → "Weakest is 4 PM to 6 PM".
   Fix (verified: all 24 tests pass with it) in `OfferMath.bestHours`, require offers in both hours of the window:
   ```kotlin
   val bands = (0 until 24).map { s -> Band(s, seen.filter { it.hour == s || it.hour == (s + 1) % 24 }) }
       .filter { b -> b.list.size >= 4 && b.list.any { it.hour == b.start } && b.list.any { it.hour == (b.start + 1) % 24 } }
   ```
2. **Medium — per hour is reported but never used to pick the best window.** Spec: best window "by average dollars per mile (and per hour when known)". A window with great $/mi but $12/hr still wins. Fix: rank by the worse of the two tiers like L2 does, e.g. `maxByOrNull { b -> minOf(b.perMile / 2.0, b.perHour?.let { it / 20.0 } ?: Double.MAX_VALUE) }` using `OfferJudge.minPerMile/minPerHour` passed in as parameters.
3. **Low — "I've only seen 1 offers".** Fix: `"I've only seen ${seen.size} offer${if (seen.size == 1) "" else "s"} so far; give me a few more dashes."` (test `l1_t2_oneOfferGrammar`).
4. **Medium (test 5 "numbers written to be spoken") — "2.80 dollars a mile".** Piper/eSpeak reads "two point eight zero dollars". Fix: replace `OfferMath.money` with spoken form: `private fun money(v: Double): String { val c = Math.round(v * 100); val d = c / 100; val r = c % 100; return if (d == 0L) "$r cents" else if (r == 0L) "$d dollars" else "$d dollars $r" }` → "2 dollars 80 a mile". Update the builder's test expecting "2.80 dollars" accordingly (that's a spec-driven change, not a weakening).
5. **Medium — saving slows the offer call-out.** `remember()` re-parses and re-writes the whole diary (up to ~100 KB JSON) on the accessibility thread before the call-out is sent. Fix: in `OfferJudge.check`, send ACTION_SAY first, then `thread { remember(...) }`; make `insights("clear")` also `@Synchronized` on the same lock so a clear can't race a save.
6. **Low — clearing has no undo.** "clear my offer diary" wipes up to 1500 offers instantly on one exact phrase. Acceptable per spec, but suggest keeping the old log under `offer_log_prev` for a day so "undo" is possible.

## Day-in-the-life scenarios
- **7 AM shift, car Bluetooth:** "Jarvis, when are my best hours?" → reflex (no Claude, instant, free) → with real data from his 7–11 shift it can answer "6 AM to 8 AM" (problem 1). Wrong answer.
- **Evening 5–9 PM, mid-delivery:** offers are saved silently while the call-out speaks; duplicates within 2 min not saved twice. Save happens before speaking (problem 5).
- **At home, Google Home / Govee:** "how have my offers been?" on the house speaker → same reflex answer. No device control involved.
- **Noisy car / mishear:** "when are my vest hours" → no reflex match → Claude → `offer_insights` summary. Works, costs one Claude call.
- **No signal:** reflex phrasings work fully offline (diary is on the phone). Other phrasings need Claude.
- **Vague ask:** "how's dashing going?" → Claude can choose `offer_insights`; fine.
- **Follow-up within 3 s:** reflex reply is added to the conversation, so "and the evenings?" goes to Claude with context. OK.
- **Misfire check:** reads/writes only local SharedPreferences; nothing sent, bought or posted. The only destructive action is "clear", which needs an explicit phrase. Safe.
- **Privacy:** raw diary stays on the phone (`allowBackup=false`). Only the one-sentence summary reaches Claude when asked through Claude, which spec item 7 requires.
